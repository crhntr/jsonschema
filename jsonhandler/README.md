# jsonhandler

Package jsonhandler renders an HTML form for any JSON Schema 2020-12 document
and turns the submitted form back into JSON that matches the schema. The form
is plain server-rendered HTML: every edit (adding an array item, switching a
`oneOf` variant, removing a map entry) is a form submission handled on the
server, so the form works without JavaScript. When [htmx](https://htmx.org)
is on the page, the same markup swaps in place and validates as you type.

The handlers are generated by [muxt](https://github.com/typelate/muxt) from
the route templates in `routes.gohtml`. The values are read and written with
`encoding/json/v2`.

```go
h, err := jsonhandler.New(ctx, schemaJSON)
if err != nil {
	return err
}
h.OnSubmit = func(ctx context.Context, v jsontext.Value) (string, error) {
	return "Saved.", store.Save(ctx, v)
}
mux := http.NewServeMux()
jsonhandler.TemplateRoutes(mux, h, "/settings")
```

`jsch form` (see the repository README) is a complete example: a page, styled
with Open Props, for editing a file against a schema, or for editing a JSON
Schema itself through the 2020-12 meta-schema.

## Endpoints

`TemplateRoutes(mux, receiver, prefix)` registers three routes under `prefix`
(joined with `path.Join`, so `""` and `"/"` both mean the root). Every response
is an HTML partial with no `<html>` or `<body>`.

| Route | Handler method | Responds with |
|---|---|---|
| `GET {prefix}/form` | `Form(ctx)` | the form for `Handler.Value`, or for the schema's `default` |
| `POST {prefix}/form` | `SubmitForm(ctx, form)` | the form again after an edit (200), the form with errors (422), or the result (200) |
| `POST {prefix}/form/validate` | `Validate(ctx, form)` | error lists only, each marked `hx-swap-oob="true"` (200) |

`POST /form` decides what to do from the `@action` control. A request with an
`@action` is an edit: the server applies it and renders the form again, with
no validation. A request without one is a submission: the server decodes the
form to JSON, validates it against the schema, calls `OnSubmit` if it is
valid, and renders the result partial. A form that would have more fields
than `Handler.MaxFields` gets 413 and an error instead of fields.

The receiver is the `RoutesReceiver` interface, so you can wrap `*Handler` to
choose the schema or initial value per request. `cmd/jsch/form.go` does this
to move `Value` forward after each save.

## Putting the form in your app

There are three ways to use the partials, and they can be mixed.

**Load it with htmx.** Mount the routes and let a placeholder fetch the form.
The form posts to its own routes and swaps itself, and after a valid
submission the result partial replaces it.

```html
<div hx-get="/settings/form" hx-trigger="load" hx-swap="outerHTML">Loading…</div>
```

htmx does not swap 4xx responses by default, and an invalid submission is a
422 with the corrected form in the body. Tell htmx to swap 422 and 413:

```html
<meta name="htmx-config" content='{"responseHandling":[{"code":"204","swap":false},{"code":"[23]..","swap":true},{"code":"413","swap":true},{"code":"422","swap":true},{"code":"[45]..","swap":false,"error":true}]}'>
```

**Render it into your own page.** `Templates()` returns a copy of the
template set. Parse your page into it and execute `jsonhandler-form` with a
`*Form`, after setting where it posts:

```go
t, err := jsonhandler.Templates()
// handle err
t, err = t.ParseFS(pages, "*.gohtml")
// handle err
paths := jsonhandler.TemplateRoutes(mux, h, "/settings")

mux.HandleFunc("GET /settings", func(w http.ResponseWriter, r *http.Request) {
	f, err := h.Form(r.Context())
	// handle err
	f.WithActions(paths.SubmitForm(), paths.Validate())
	err = t.ExecuteTemplate(w, "settings-page", f)
	// handle err
})
```

```gotemplate
{{define "settings-page"}}<!doctype html>
<html><head>…</head><body><main>{{template "jsonhandler-form" .}}</main></body></html>
{{end}}
```

`WithActions(submit, validate)` sets the form's `action` and `hx-post`, and
the live validation endpoint. Pass an empty `validate` to turn validation as
you type off.

**Use the handler directly.** `Handler.SubmitForm` and `Handler.Validate` take
`url.Values`, so your own handler can call them and render the result however
you like. `Form.Valid` and `Form.Value` hold the outcome.

Without htmx the form still works: buttons submit the whole form to `POST
/form`, the server renders the form or the result, and the browser shows it as
a page. That response is a partial, so either let htmx swap it or have your
page handler wrap the partial in a document.

## How the form maps to the schema

The form for a location is chosen from the schema at that location after
`$ref` and `$dynamicRef` are followed (`$dynamicRef` resolves through the
dynamic scope, so recursive meta-schemas work) and `allOf` members are merged.
For single-valued keywords such as `title`, the schema's own keyword wins
over one reached through a reference, which wins over one from an `allOf`
member. `properties` and `required` are combined.

| Schema | Kind | Control |
|---|---|---|
| `const` | `const` | the value, read-only |
| `enum` | `select` (or `radio`) | one option per value, plus a blank one |
| `oneOf` / `anyOf` | `choice` | a variant picker and the chosen variant |
| `type` with several types | `choice` | one variant per type |
| `type: "string"` | `text` | `<input>`, typed by `format` (see below) |
| `type: "number"` / `"integer"` | `number` | `<input type="number">` |
| `type: "boolean"` | `checkbox` | a checkbox |
| `type: "null"` | `null` | the text `null` |
| `type: "object"` with `properties` | `object` | a group of fields |
| `type: "object"` without `properties` | `map` | a list of name/value entries |
| `type: "array"` | `array` | an ordered list of items |
| `type: "array"`, `uniqueItems`, `items.enum` | `checkboxes` | one checkbox per value |
| `true`, `{}`, or anything else | `json` | a `<textarea>` holding JSON |

Without a `type`, the kind is inferred from keywords that only apply to one
type (`properties` means object, `items` means array, `pattern` means string,
`minimum` means number). A nullable scalar such as `["string","null"]` stays a
text input: left blank, a required one is `null` and an optional one is left
out. A nullable object, array or boolean becomes a choice with a `null`
variant.

Keywords become attributes so the browser can help before the server checks:

| Keyword | Attribute |
|---|---|
| `title` | the label (the property name when there is no title of its own) |
| `description` | a `.jsonform-description` paragraph, linked by `aria-describedby` |
| `required` | `required` when every enclosing value is required too, plus a `*` mark |
| `default` | the initial value when required, the placeholder when optional |
| `examples[0]` | the placeholder when there is no default |
| `readOnly` | `readonly` (or `disabled` with a hidden input for checkboxes and selects) |
| `writeOnly` | `type="password"`, and the value is never sent to the browser |
| `deprecated` | `data-deprecated`; optional deprecated values start collapsed and sort last |
| `minLength` / `maxLength` | `minlength` / `maxlength` |
| `pattern` | `pattern=".*(?:…).*"`, since JSON Schema patterns match anywhere |
| `minimum` / `maximum` | `min` / `max` (and `exclusive*` for integers) |
| `multipleOf` | `step`, when `min` is a multiple of it |
| `format: email` / `uri` / `date` / `date-time` / `time` | `type="email"` / `url` / `date` / `datetime-local` / `time` |
| `propertyNames.pattern` | `pattern` on a map entry's name input |

`date-time` and `time` values are shown and read in UTC, because the browser
controls have no time zone.

The `required` attribute is only set when the whole chain of enclosing values
is required. An optional address with a required street must not stop the
browser from submitting a form where the address is left blank.

### Optional values

An optional value is left out of the JSON when nothing was entered for it. For
an object that means none of its fields were filled in (an unchecked checkbox
does not count), so an optional object with a required field can be left blank
without an error. An unchecked optional checkbox is left out unless its default
is `true`.

Some optional values start *collapsed*, as a label and an Add button:
deprecated keywords, values whose schema repeats an enclosing schema (which
would otherwise expand forever), and anything annotated `"collapsed": true`.
Once added, they have a Remove button.

Objects with more than 12 properties go further. Their optional properties
without a value are not rendered at all; an "Add a property" picker lists them
instead. This keeps a form for a wide schema, like the meta-schema, at the
size of the data rather than the size of the schema.

### Validation

A submission is validated in two steps. Decoding catches what cannot become
JSON at all (a number field that is not a number, JSON that does not parse,
a map entry with no name or a duplicate name, a required value left blank).
If decoding succeeds, the JSON is validated against the schema with
`Schema.Validate`, and each error is shown on the field at its
`instanceLocation`. An error at a location without a field of its own goes to
the nearest enclosing field, prefixed with its location, for example
`/address/zip: …` on a JSON text area. For a `oneOf` or `anyOf`, only errors
from the chosen variant are shown.

`POST /form/validate` runs the same checks without submitting, but holds back
errors that only say a value is missing, which would otherwise appear for
every field the moment someone starts typing.

### JSON mode

The Edit as JSON button replaces the fields with one text area holding the
value they decode to, and Edit as form goes back. The text area is submitted
and validated like any other JSON field. Switching to JSON fails, keeping the
fields, if a field cannot be decoded; switching back fails, keeping the text,
if it does not parse.

### Hiding groups

With `Handler.Outline` on, each outline entry has a Hide button. A hidden
group shrinks to one row, in the outline and in the form, with a summary (how
many items or properties, or the chosen variant) and a Show button. Hiding
changes nothing about the value: the group's controls stay in the page as
hidden inputs, and the hidden state is itself a control (`@folded/path`), so
it lasts across edits and submissions.

### Wizard

Edit with wizard shows one group at a time. A step shows the group's own
fields and, for each group inside it, a row with an Edit button that steps
into it. A breadcrumb leads back up, Back and Next go through the groups in
document order, and in the outline every group is a button that goes to its
step. In the fields view, each outline entry has an Edit button that opens
the wizard right at that group.

The page holds the whole value. Everything outside the current step is
carried as hidden inputs, so leaving a step loses nothing, and the step
itself is two controls, `@mode=wizard` and `@step=/path`. Submit validates
the whole value from any step. Errors on the step show on its fields, and
the other steps with errors are listed with buttons that go to them (moving
to a step checks it the way validation as you type does). Edit as form and
Edit as JSON work from any step.

`writeOnly` values are never written into hidden inputs, so one entered on a
step is kept only while that step is the one being submitted.

### Why something is not available

The form says why a control does nothing rather than leaving it out without
a word:

- An Add item or Add property button that would break `maxItems`,
  `maxProperties`, a closed tuple (`items: false`) or
  `additionalProperties: false` is rendered disabled, with the reason next to
  it.
- A `readOnly` field says "Read-only".
- Only the chosen `oneOf`/`anyOf` variant's fields are rendered, and the
  choice says which variants are not in use and that switching the variant
  is how to fill them in instead. The outline shows the chosen variant next
  to each choice and only its branch of the tree.

## Markup reference

This is the contract a stylesheet can rely on. Class names start with
`jsonform-`. The templates add no inline styles, and nothing about how the form
behaves depends on CSS.

### The form

```html
<form class="jsonform" id="jsonform" method="post" action="/form"
      hx-post="/form" hx-target="this" hx-swap="outerHTML"
      data-mode="json"?  data-invalid?>
  <button type="submit" hidden …></button>            <!-- default button for Enter -->
  <div class="jsonform-live" hidden hx-post="/form/validate" …></div>
  <div class="jsonform-toolbar">
    <button class="jsonform-button jsonform-mode" name="@action" value="json">Edit as JSON</button>
  </div>
  <nav class="jsonform-outline" aria-label="Outline">…</nav>   <!-- Handler.Outline -->
  <div class="jsonform-body">
    <ul class="jsonform-errors" id="jsonform_errors" role="alert" hidden?>…</ul>
    <!-- the root field -->
    <div class="jsonform-actions">
      <button type="submit" class="jsonform-button jsonform-submit">Submit</button>
    </div>
  </div>
</form>
```

The first button is a hidden submit button. Pressing Enter in a text input
clicks the form's first submit button, and without it that could be an Add or
Remove button.

### Every field

Each location in the value is one element with class `jsonform-field`: a
`<div>` for a single control and a `<fieldset>` for a group (object, map,
array, choice, radio group, checkbox group).

| Attribute | Meaning |
|---|---|
| `data-kind` | the kind from the table above: `text`, `textarea`, `number`, `checkbox`, `select`, `radio`, `checkboxes`, `const`, `null`, `json`, `object`, `map`, `array`, `choice` |
| `data-pointer` | the JSON Pointer of the location in the value (`""` for the root) |
| `data-required` | the schema requires the value |
| `data-invalid` | the field has errors |
| `data-deprecated` | the schema marks it `deprecated` |
| `data-readonly` | the schema marks it `readOnly` |
| `data-collapsed` | an optional value that is left out, shown as an Add button |
| `class` | `jsonform-field`, plus any `x-form` `class` |

Inside, in this order:

| Element | Class | Notes |
|---|---|---|
| `<label>` or `<legend>` | `jsonform-label` | contains `<abbr class="jsonform-required">*</abbr>` when required |
| `<input>`, `<select>`, `<textarea>` | `jsonform-control` | `id` is the field's id; `aria-invalid="true"` when invalid |
| `<p>` | `jsonform-description` | `id` is the field's id + `_help` |
| `<ul>` | `jsonform-errors` | always present, `hidden` when empty, `id` is the field's id + `_errors` |
| `<button>` | `jsonform-button jsonform-remove` | only on optional values that were added |

A checkbox puts the `<input>` before its `<label>`. Groups also carry
`id` = the field's id + `_group`, which the outline links to.

### Field ids

A field's id is the form id followed by its form path, with `/` written as
`-`, letters and digits kept, and any other byte written as `_` and two hex
digits: `/address/street` is `jsonform-address-street` and `/$id` is
`jsonform-_24id`. The root is `jsonform_root`. Suffixes for related elements
(`_errors`, `_help`, `_label`, `_group`, `_key`, `_pick`, `_value`) start with
`_` and a letter that is not a hex digit, so no two elements collide, and every
id is a valid CSS identifier.

### Kinds

**text, number** use `<input class="jsonform-control" type="…">`. **textarea, json**
use `<textarea class="jsonform-control">`; json adds `spellcheck="false"`.

**checkbox** renders a hidden `false` input followed by the checkbox with value
`true`, so an unchecked box still submits a value.

**select** renders a `<select>` whose first option is blank (its text is the
default, if any). **radio** and **checkboxes** render a `<fieldset>` with a
`<legend>` and `<div class="jsonform-options">` of
`<label class="jsonform-option"><input …> text</label>`.

**const** and **null** render `<span class="jsonform-label">` and
`<output class="jsonform-const">` (or `jsonform-null`).

**object** renders a `<fieldset>` with its fields in schema order (deprecated
ones last). A wide object adds a picker:

```html
<div class="jsonform-pick">
  <label class="jsonform-label" for="…_pick">Add a property</label>
  <select class="jsonform-control" id="…_pick" name="@pick/path">…</select>
  <button class="jsonform-button jsonform-add" name="@action" value="pick/path">Add</button>
</div>
```

An object's properties that the schema does not declare (allowed by
`additionalProperties`, or present in the value) follow as entries, like a map.

**map** renders a `<fieldset>` containing:

```html
<div class="jsonform-entries">
  <input type="hidden" name="@len/path" value="2">
  <ol class="jsonform-items">
    <li class="jsonform-item jsonform-entry">
      <div class="jsonform-key">
        <label class="jsonform-label">Property name</label>
        <input class="jsonform-control" name="@key/path/~k0">
        <ul class="jsonform-errors">…</ul>
      </div>
      <!-- the value's field -->
      <div class="jsonform-item-actions">…</div>
    </li>
  </ol>
  <button class="jsonform-button jsonform-add" name="@action" value="add/path">Add property</button>
</div>
```

**array** renders a `<fieldset>` with the same `<ol class="jsonform-items">`,
items as `<li class="jsonform-item">`, and an Add item button.
`.jsonform-item-actions` holds `jsonform-up`, `jsonform-down` and
`jsonform-remove` buttons; the first item's up and the last item's down are
`disabled`.

**choice** renders a `<fieldset>` with:

```html
<div class="jsonform-variant">
  <label class="jsonform-label">Variant</label>
  <select class="jsonform-control" name="@variant/path" hx-post=… hx-trigger="change">…</select>
  <button class="jsonform-button jsonform-refresh" name="@action" value="refresh">Change</button>
</div>
<!-- the chosen variant's field, labeled with the variant's name -->
```

Without JavaScript you pick a variant and press Change; with htmx the change
alone re-renders the form.

### Buttons

Every button has `jsonform-button` and one of: `jsonform-submit`,
`jsonform-add`, `jsonform-expand`, `jsonform-remove`, `jsonform-up`,
`jsonform-down`, `jsonform-refresh`, `jsonform-mode`, `jsonform-edit`,
`jsonform-step`, `jsonform-fold`, `jsonform-unfold`, `jsonform-back`,
`jsonform-up-step`, `jsonform-next`. Edit buttons carry `formnovalidate`,
so the browser does not block an Add because some other field is not filled
in yet. An Add button that cannot be used is `disabled` and
`aria-describedby` a `<span class="jsonform-reason">` saying why.

### Reasons

`<span class="jsonform-reason">` explains a disabled Add button or a
`readOnly` field ("Read-only"). A choice with more than one variant has
`<p class="jsonform-reason jsonform-inactive">` naming the variants not in
use.

### Stubs

A hidden group, or a group below the wizard's step, is one row:

```html
<div class="jsonform-field jsonform-stub" id="…_group" data-kind="object"
     data-pointer="/address" data-stub data-folded? data-invalid?>
  <span class="jsonform-label">address</span>
  <span class="jsonform-summary">3 items</span>                <!-- arrays, maps, choices -->
  <button class="jsonform-button jsonform-unfold" value="unfold/address">Show</button>  <!-- hidden -->
  <button class="jsonform-button jsonform-step" value="step/address">Edit</button>      <!-- wizard -->
  <input type="hidden" name="$/address/street" value="…">…
</div>
```

`data-invalid` on a stub means there are errors somewhere inside it.

### Outline

```html
<nav class="jsonform-outline" aria-label="Outline">
  <ol>
    <li data-invalid? data-folded? aria-current="step"?>
      <a class="jsonform-outline-label" href="#jsonform-address_group">address</a>
      <span class="jsonform-note">Dog</span>                      <!-- a choice's variant -->
      <button class="jsonform-button jsonform-step" value="step/address">Edit</button>
      <button class="jsonform-button jsonform-fold" value="fold/address">Hide</button>
      <ol>…</ol>                                                  <!-- left out when hidden -->
    </li>
  </ol>
</nav>
```

The outline lists every object, map, array and choice, nested as they are.
`data-invalid` marks a group with an error anywhere inside it. In the
wizard the label is a `<button class="jsonform-button jsonform-step
jsonform-outline-label">` that goes to the step, there is no separate Edit
button, and `aria-current="step"` marks the current step.

### Wizard

In the wizard the form has `data-mode="wizard"` and its body starts with:

```html
<input type="hidden" name="@mode" value="wizard">
<input type="hidden" name="@step" value="/address">
<nav class="jsonform-crumbs" aria-label="Steps">
  <ol>
    <li><button class="jsonform-button jsonform-step" value="step">Person</button></li>
    <li aria-current="step"><span class="jsonform-label">address</span></li>
  </ol>
</nav>
<div class="jsonform-elsewhere" role="alert">                     <!-- other steps with errors -->
  <p>These steps have errors too:</p>
  <ul><li><button class="jsonform-button jsonform-step" value="step/tags">tags</button></li></ul>
</div>
<input type="hidden" name="…" value="…">…                         <!-- everything outside the step -->
<!-- the step's field -->
<div class="jsonform-actions">
  <button class="jsonform-button jsonform-back" value="step">Back</button>
  <button class="jsonform-button jsonform-up-step" value="step">Up to Person</button>
  <button class="jsonform-button jsonform-next" value="step/tags">Next: tags</button>
  <button type="submit" class="jsonform-button jsonform-submit">Submit</button>
</div>
```

### Result

```html
<div class="jsonform-result" id="jsonform">
  <output class="jsonform-output"><pre><code>{ … }</code></pre></output>
  <p class="jsonform-message" role="status">Saved.</p>
  <form method="post" action="/form" …>
    <input type="hidden" name="…" value="…">…
    <button class="jsonform-button jsonform-edit" name="@action" value="edit">Edit</button>
  </form>
</div>
```

The result has the form's id, so htmx swaps back and forth in the same place.
The Edit button re-opens the submitted form. `writeOnly` values are shown as
`"********"` and are not in the hidden inputs.

### Live validation response

`POST /form/validate` responds with one `<ul class="jsonform-errors">` per
rendered field and map entry name, plus the form's own list, each with its id
and `hx-swap-oob="true"`, so htmx replaces the error lists and leaves the
controls, focus and caret alone. Only error lists change; `data-invalid` and
`aria-invalid` are updated by the next full render.

## Form state

Control names are *form paths*: JSON Pointers into the value, except that map
entries are addressed by position as `~k0`, `~k1`, … because their names are
themselves form input. A pointer built from a property name escapes `~` as
`~0`, so `~k` cannot collide with a property.

| Name | Holds |
|---|---|
| `$path` | the value of a scalar control (`$` alone is the root) |
| `@len/path` | the number of array items or map entries |
| `@variant/path` | the chosen variant of a choice, by index |
| `@present/path` | an optional object, array or map that was added |
| `@key/path` | the property name of the map entry at `path` |
| `@pick/path` | the property to add to the wide object at `path` |
| `@folded/path` | the group at `path` is hidden |
| `@mode` | `json` while the form shows one JSON text area, `wizard` in the wizard |
| `@step` | the form path of the wizard's current group |
| `@action` | the edit an edit button asks for |

`@action` values are an operation followed by a path:
`add/tags`, `remove/tags/2`, `up/tags/2`, `down/tags/2`, `expand/next`,
`pick/` + object path (`pick` alone for the root), `fold/address`,
`unfold/address`, `step/address` (opens the wizard at that group; `step`
alone is the root), `json`, `fields`, and `refresh` or `edit`, which change
nothing and re-render.

Other request fields are ignored, so a CSRF token field can sit in the same
form.

## Annotations

The `x-form` keyword adjusts presentation. It never changes the JSON the form
produces. A malformed `x-form` is ignored.

```json
{
  "type": "object",
  "x-form": {"order": ["email", "name"]},
  "properties": {
    "name": {"type": "string"},
    "email": {"type": "string", "format": "email", "x-form": {"placeholder": "you@example.com"}},
    "bio": {"type": "string", "x-form": {"widget": "textarea", "rows": 6}},
    "size": {"enum": ["s", "m", "l"], "x-form": {"widget": "radio"}},
    "notify": {"type": "boolean", "x-form": {"widget": "select"}}
  }
}
```

| Member | Effect |
|---|---|
| `widget` | `textarea`, `json`, `radio`, `select` (booleans: true/false/unset), `list` (an array of enum values as a list instead of checkboxes), or an input type: `password`, `email`, `url`, `tel`, `search`, `color`, `date`, `time`, `datetime-local`, `month`, `week`, `range`, `hidden` |
| `label` | the label, instead of `title` or the property name |
| `placeholder` | the placeholder |
| `order` | property names to show first; the rest follow in schema order |
| `class` | extra classes on the field element |
| `collapsed` | `true` starts an optional value collapsed; `false` always shows it, even in a wide object |
| `rows` | rows of a textarea or JSON field |

`schema.json` (served by `MetaSchema()`) is the 2020-12 meta-schema with
`x-form` added, so a form for it edits schemas, annotations included.

## Styling

`jsonform.css` (served by `Stylesheet()`) is a starting point built on
[Open Props](https://open-props.style). Load Open Props first, then the file,
or copy it and change it. Everything it does goes through the hooks above, so
a stylesheet written from scratch gets the same behavior.

It reads these custom properties, which you can set on `.jsonform` or any
ancestor: `--jsonform-font`, `--jsonform-mono`, `--jsonform-text`,
`--jsonform-muted`, `--jsonform-surface`, `--jsonform-control`,
`--jsonform-border`, `--jsonform-accent`, `--jsonform-accent-text`,
`--jsonform-error`, `--jsonform-radius`, `--jsonform-gap`, and
`--jsonform-indent`. Dark values apply under `prefers-color-scheme: dark`.

Some things it does that you may want to keep in your own:

- Groups get a rule down their start edge instead of a padded box, so deeply
  nested values keep most of the width.
- `.jsonform-body > fieldset` (the root group) has no rule.
- With an outline, wide screens show it as a sticky sidebar.
- In JSON mode the root's error list is moved above the text area with
  `order: -1`.

## Security

- **readOnly.** A submission cannot change, add or remove a `readOnly`
  value. After decoding, every `readOnly` location in `Handler.Value` or in
  the submission is restored from `Handler.Value` (or the schema default) by
  JSON Pointer, or removed if the original lacks it. Array items are matched
  by position.
- **writeOnly.** These values are never encoded into the form, echoed after an
  edit or an error, put in the result's hidden inputs, or shown in the result.
  A `writeOnly` field starts empty, and left empty it is left out, so treat a
  missing value as unchanged.
- **Size.** The form state decides how many items and entries to render, so
  `MaxFields` (default 10000) bounds the work a request can cause, including
  schemas whose required properties recurse.
- **CSRF.** The routes accept posts like any form. Protect them as you protect
  the rest of your app, for example with `http.CrossOriginProtection`, which
  `jsch form` uses.
- **Schemas.** `New` resolves references only within the document and to the
  built-in 2020-12 meta-schemas, and never fetches over the network.

## Testing

`go test ./jsonhandler` renders forms over HTTP and parses them with
[`typelate/dom`](https://github.com/typelate/dom). The tests round-trip
values (including every 2020-12 meta-schema document through the
meta-schema's own form), check the markup contract above for every kind,
and fuzz both submissions (`FuzzSubmitForm`) and encodings (`FuzzEncode`).

Two kinds of mutation testing check that the tests notice changes:

```sh
# Go code
gremlins unleash ./jsonhandler --exclude-files 'template_routes\.go$' --timeout-coefficient 30

# Templates
go tool muxt -C jsonhandler test-template-mutations
```

muxt is pinned in `go.mod` as a tool. Its template checker,
`github.com/typelate/check` v0.8.1, recurses without end on templates
that invoke themselves, as `jsonhandler-field` does, so `muxt check` and
`test-template-mutations` overflow the stack until it learns to stop at a
template already being checked with the same type of dot. `muxt generate`
is not affected.

## Limitations

- `if`/`then`/`else`, `not`, `dependentSchemas`, `patternProperties`,
  `contains` and `unevaluated*` do not change the form; the validator still
  enforces them.
- A checkbox group submits values in `enum` order, not the order they had.
- Output objects list members in schema order, not the order of
  `Handler.Value`.
- A map entry cannot have an empty property name.
- Validation as you type updates error lists but not `data-invalid` or
  `aria-invalid`.
- The UI strings ("Add item", "Remove", "Variant", …) are English.
